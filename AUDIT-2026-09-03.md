# Audit, 2026-09-03

Every document in this repository was read against the code, the tests and the committed benchmark
data on 2026-09-03, and every claim that carries a number or names a behaviour was checked against
the file it rests on. Thirteen defects were recorded across three passes, and all
thirteen are corrected.

## What was wrong and what changed

### 1. A raw byte in a rejected ack

`Reader::expect` built "expected ',', got 'X'" and `append_escape` built "invalid escape: \X" by
splicing a byte straight out of the frame, and `serve_connection` copies that message into the ack's
`reason`. A frame such as `{"schema_version":4\xff}` produced an ack body that
`orjson.loads` refuses as invalid UTF-8, and the poller has to load the whole frame before it
reaches the reason it logs. Both sites now render the byte through a `hex_byte` helper, so the three
frames that reached them produce `expected ',', got byte 0xff`, `expected ':', got byte 0xc3` and
`invalid escape: byte 0xff`. `tests/test_executor.cpp` drives those three frames over a socket and
checks the ack is valid UTF-8 with a UTF-8 validator written for the test.

### 2. The asyncio figures

README.md and RESULTS.md led with "a factor of 2.4 to 5.0 depending on the event loop and the
percentile" and with a `wake_recv` reading of 1.2us under a stock asyncio poller. Both RESULTS.md
configuration tables are headed "under uvloop" and `bench_history.csv` holds five C++-side rows, so
the 5.0x, the 1.2us and the 0.7us measurement floor derived from it appear nowhere in this
repository. The asyncio half was removed. The headline is now 2.4x at p99 and 2.8x at p50 under
uvloop, the floor argument names two clients instead of three, and the floor is 0.3us.

### 3. The 84 percent split

RESULTS.md decomposed `wake_recv` as 84 percent `decode` and 5 percent `encode_ack` twelve
paragraphs after saying that any claim about `wake_recv` finer than "between 1 and 2 microseconds"
is reading noise. Both inputs come from the CSV rounded to 0.0001 ms, and `decode` and `wake_recv`
are separate measurements, one a hot-cache loop with no socket in it. The percentages are gone from
both documents. The sentence now says `decode` accounts for most of `wake_recv` and `encode_ack` for
a small remainder, states that the figures are rounded to 100ns and separately measured, and says no
percentage split should be read off them.

### 4. The repeat run

RESULTS.md offered a repeat benchmark run in place of the pre-registered fresh boot and said "a
reader can check that agreement", while `bench_history.csv` carries five rows under one timestamp
and the second run was never written to it. The claim was corrected instead of the data. The
sentence now says the four percentages are the only record of the second run and that nobody can
check them.

### 5. The legacy frames

Only the v1 case asserted all eight later fields. The v2 case left out
`available_size_contracts` and `price_ranges`, which are also post-v2 additions, and no legacy case
asserts full equality. Both missing checks were added to the v2 case, and README.md now says the v1
frame asserts every field added since, the v2 and v3 frames assert the fields added after each of
them, and full equality is asserted against the five message shapes and the two acks.

### 6. Naming the field

The reason names a field for `UnknownField` and `MissingField` and nothing else. A parse failure
yields "expected a string" or similar, and the test only asserted that the reason is non-empty.
README.md now says the reason names the field when the failure is a missing or unexpected one and
names the parse error otherwise.

### 7. clock_domain

`compute_clock_domain` floors the boot epoch into 60-second buckets, so the header's example
`gethostname():1787290000` is a value it cannot return. The example is now `gethostname():1787289960`
and the comment says the epoch is floored to a 60-second bucket. `clock_domain()` has no caller in
`src/`, `bench/`, `include/` or `tests/`, so the header now says nothing in this process consumes
the token yet.

### 8. 1181 against 1186

The comment in `src/executor.cpp` and the sentence in BENCHMARK.md describe one observation and gave
two values five milliseconds apart. The source comment now reads 1186 ms, matching BENCHMARK.md.

### 9. The double buffer comment

`src/json.hpp` said `format_double` can produce 25 bytes. The longest fixed case is 24 bytes and so
is the longest scientific case. The comment now says 24. `kDoubleBufferSize` was 32 before and after,
so no behaviour changed.

### 10. The 2.4 to 2.8 range

The three uvloop ratios are 2.81 at p50, 2.95 at p90 and 2.38 at p99, so a reader dividing the p90
column of the table three lines below lands outside the range the sentence gave. README.md now names
the two percentiles it quotes instead of stating a range.

### 11. Both figures

The round-1 rewrite of the component paragraph stripped the figures out of the README copy and left
"Both figures are rounded to 100ns" with nothing to refer to except two `wake_recv` readings from
two clients. The figures were restored, so the README sentence matches the one in RESULTS.md.

### 12. The missing percentile

"0.0045ms to 0.0016ms" is the p50 pair and the opening sentence no longer said so once the ratios
were split by percentile. The sentence now ends "at p50".

### 13. What can reach the wire

PORT-FIDELITY.md said every string the executor puts on the wire is its own ASCII or a
`correlation_id` off a decoded frame. A rejected ack's reason can also carry a field name, and
round 2 added that to the list. The list is still short by one entry, because the reason can carry
a decoded string value as well: `read_direction` in `src/protocol.cpp` builds "direction must be
yes or no, got X" out of the frame's own `direction` field, which was confirmed live with a
multi-byte value in that field. `read_status` at `src/protocol.cpp:184` builds its reason the same
way. That string went through `scan_string` and is valid UTF-8, so the paragraph's conclusion holds
and only its enumeration was wrong. The field-name clause now reads "or a field name or string value
off a decoded frame", which covers both cases.

## What was checked and found correct

The four presets the README documents configure, build and pass from a cold checkout on Ubuntu
24.04 with cmake 3.28.3, gcc 13.3 and clang 18.1.3: `dev`, `release`, `ubsan` and `asan-ubsan`, each
92 of 92 tests and 44,305 assertions, none skipped. The warning set in
`cmake/CompilerWarnings.cmake` produced zero warnings under both compilers with `HOTPATH_WERROR=ON`.
The `asan-ubsan` preset passes with `detect_leaks=1 halt_on_error=1 strict_init_order=1`, and the
benchmark binary runs clean under it. clang-format 23.1.0 and clang-tidy 22.1.8, the pinned
versions, report nothing on this tree, with the compilation database generated by clang as the CI
lint job does it.

Every cell of the RESULTS.md `decode`, `encode_ack`, `sign`, `roundtrip` and `wake_recv` tables
matches `bench_history.csv` exactly, and the ratios stated in prose follow from the tables: 2.81 and
2.38 for the uvloop `wake_recv` pair, 2.09 for `wake_send` at p50, 2.80 for the `sign` row, 1.3
percent between `openssl speed` and this port's signer, 0.3 percent for the `sign` control across
the executor swap.

All ten golden frames carry a correct 4-byte big-endian prefix equal to the body length, and
`orjson.dumps(orjson.loads(body))` reproduces each body byte for byte under orjson 3.12.0, so the
field-order claim and the byte-identical encoder claim hold. All 1,000 rows of
`tests/golden/doubles.tsv` match orjson's output on this machine with no disagreements. The v1, v2
and v3 legacy cases assert the fields the README now says they assert, and the five message shapes
and two acks assert full equality through `check_round_trip`.

The executor was run end to end over a Unix socket. Seven malformed and rejected frames each
produced a valid UTF-8 ack: three hex-escaped byte errors, a decoded enum value, an unexpected
field, a missing field, and a truncated document. A five-wake run reproduced the counter block in
the README verbatim, and the telemetry file it wrote carries `user_version` 6, WAL journalling, the
`latency_events` table and five rows.

No intra-repo link in any document points at a file that does not exist. BENCHMARK.md sections 1
through 8 were not touched by either fix round, so the pre-registration still reads as it was
committed.

## What this repository cannot settle

The py-to-py and py-to-cpp rows, the `wake_send` table, the `cryptography` row of the `sign` table
and the `openssl speed` figure were all produced by `benchmarks/latency_bench.py` in
`prediction-market-infra` on an Apple silicon Mac, and none of their raw rows are committed here.
They were checked for internal consistency and for arithmetic against each other, and nothing more
than that is possible from inside this repository. The absolute numbers do not reproduce on other
hardware and the documents do not claim they will. The second benchmark run described in RESULTS.md
has no committed rows, which RESULTS.md now says. Regenerating the fixtures against
`prediction-market-infra` at `e3fd937` was not attempted, because that repository was not reachable
from the machine this audit ran on. Separating the language change from the process separation
needs a py-to-py configuration that does not exist, which RESULTS.md lists as the first of the three
things that would have to change.
